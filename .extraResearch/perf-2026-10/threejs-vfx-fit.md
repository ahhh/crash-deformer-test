# awesome-threejs-vfx fit review (crash-deformer-test, three 0.186)

Source list: https://github.com/naranyala/awesome-threejs-vfx (CC0, 6 stars, 2 forks; an index of ~120 links, not a code library). Facts below come from the GitHub API, the npm registry and READMEs fetched 2026-10-12. `[INFERENCE]` marks anything not verified from a source.

## Result: no FIT

Nothing in the list cuts a measured cost. The costs we measured are CPU-side: sim (53 % / 59 %), per-object matrix and geometry updates, draw-call and uniform overhead, ragdoll proxy colliders. The list is mostly shader/visual effects, React wrappers and tutorials. The few perf-shaped entries either duplicate something we already have (batched or instanced particles, a merged post chain) or work on a data model we do not use (our sim queries are analytic patches, not three meshes).

## Notes on the one MAYBE worth a measurement (Rapier bump)

Verified from `bindings/typescript/CHANGELOG.md` and rapier's `CHANGELOG.md`:

- JS `0.20.0` updates to Rapier core 0.35.0: "rewritten sleeping (persistent islands), a sweep-based CCD now enabled by default against fixed colliders, a reworked narrow-phase/solver and a broad phase tuned for large mostly-static worlds."
- Core 0.35.0: "The broad phase no longer creates pairs between colliders attached to the same rigid-body"; their repro (2,210 convex colliders on one always-awake body) "steps ~90x faster while stationary and ~18x faster while moving". Also "Improved 3D solver performance by caching the constraints angular jacobians".
- JS `0.21.0` (core 0.36.0) adds soft bodies/FEM; "the npm builds enable `fem`". The unpacked package of `rapier3d-simd` goes 2.9 MB (0.19.3) to 5.2 MB (0.21.0) per the npm registry.
- Breaking for us (from the changelog): `IntegrationParameters.minIslandSize` removed (we do not appear to set it: our code sets `numSolverIterations` and `numInternalPgsIterations`, `engine-ragdoll.ts:378-380`); `NarrowPhase.contactPair` signature and solver-contact semantics changed; several contact and sleeping defaults changed.

Why it might help (hypothesis, [INFERENCE]): `engine-ragdoll.ts` already measured that each proxy collider costs every `world.step()` (4,362 colliders: 35 ms; 266 colliders: 0.8 ms), and each car's proxy is up to 128 cuboids on one kinematic body. The same-body pair fix in 0.35 targets exactly "many colliders on one body", but the repro is an always-awake dynamic body; whether our kinematic car bodies and collision groups (`setCollisionGroups(carGroups(i))`) already avoid those pairs is not verified.

Measure before deciding: same Fleet 32-car aftermath scene, `0.19.3` vs `0.21.0`, ms per `world.step()` (Rapier's `World.timing*` needs `profilerEnabled`), the wasm size and load time on the phone, and replay/ragdoll behavior diffs from the changed sleeping and CCD defaults. If the step is not the bottleneck it will not move the 14 fps, since the Fleet frame is 59 % sim and 27 % ragdoll with only 11 % in wasm.

## What would actually address the measured costs (outside the list)

- Fleet at 14 fps is dominated by our own sim code (rigid step surface queries, cage refit/rasterise, car-car SAT) and the JS proxy-collider fitting. No library in the list touches those.
- Render CPU (28 %): the items listed (`updateMatrixWorld`, `projectObject`, `setProgram`, uniforms) scale with scene-graph object and draw counts. The list has no batching or scene-graph tool; three's own `BatchedMesh` (already used in `TerrainBatch`, `track-ground.ts:584`) is the in-tree lever, [INFERENCE] but cars' per-vertex WASM skin deformation and distance cuts would constrain it.
